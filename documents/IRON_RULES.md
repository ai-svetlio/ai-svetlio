# 🔒 SVETLIO IRON RULES v2.1.0

**Тези правила са ЗАДЪЛЖИТЕЛНИ за всички AI агенти, работещи с AI_Svetlio.**
**Нарушаването им води до загуба на данни, счупен код и разочаровани потребители.**

> ⚠️ **Този файл се ГЕНЕРИРА.** Не го редактирай на ръка — промените се губят при следващото
> генериране. Текстът на правилата живее в `src/rules.ts`; обясненията и примерите —
> в `documents/rules-examples/NN.md`. Регенериране: `npm run gen:docs`.

## ПАМЕТ И КОНТЕКСТ

### 1. ПАМЕТ ПЪРВО

Винаги започвай от .memory/STATE.md и MODE.md

```
ВИНАГИ започвай сесия с:
1. Прочети .memory/STATE.md → Къде сме?
2. Прочети .memory/MODE.md → В какъв режим сме?
3. Прочети .memory/TODO.md → Какво остава?

НИКОГА не работи "на парче" без контекст.
```

**Пример:**
```
❌ ГРЕШНО: "Да, ще оправя този бъг" (без да знае контекста)
✅ ПРАВИЛНО: "Първо да проверя STATE.md... Виждам че работим по X. Да продължа ли?"
```

---

### 2. НЕ ГАДАЙ

Чети ARCHITECTURE.md, не търси "на посоки" (ls -R, find /)

```
ЗАБРАНЕНО е да търсиш файлове "на посоки":
- ls -R
- find / -name "*.py"
- Пробване на случайни пътища

ПЪРВО чети:
- .memory/ARCHITECTURE.md
- README.md
- Или ПИТАЙ потребителя
```

**Пример:**
```
❌ ГРЕШНО: "Нека видя... ls src/... ls lib/... ls utils/..."
✅ ПРАВИЛНО: "Къде се намира този файл? Да проверя ARCHITECTURE.md"
```

---

### 3. ПРОЧЕТИ ЦЕЛИЯ КОД

Преди редакция, прочети целия файл. Ако е >150 реда → направи summary първо

```
ПРЕДИ да редактираш файл → ПРОЧЕТИ ГО ЦЕЛИЯ

Ако файлът е > 150 реда → направи SUMMARY първо:
- Какви функции/класове има?
- Какви imports/dependencies?
- Къде се извиква този код?
- Какви странични ефекти може да има?

НИКОГА не редактирай "на парче" без пълен контекст.
```

**Пример:**
```
❌ ГРЕШНО: "Виждам функцията на ред 45, ще я оправя" (без да знае останалото)
✅ ПРАВИЛНО: "Файлът е 200 реда. Да го прочета целия първо, за да разбера логиката"
```

---

### 4. CONTEXT REFRESH

На всеки ~15 съобщения прочети .memory/ отново и потвърди с потребителя

```
АВТОМАТИЧНО освежаване при:
- Всеки ~15 съобщения
- Или когато агентът "усети" че губи нишката
- Или когато потребителят каже "провери контекста" / "refresh"
- Или след грешка/объркване

КАКВО ПРАВИ АГЕНТЪТ:
1. СТОП — спира текущата работа
2. ПРОЧИТА:
   - .memory/STATE.md
   - .memory/MODE.md
   - .memory/TODO.md
   - .memory/PROBLEMS.md
   - .memory/DECISIONS.md
   - .memory/REFRESH_REMINDER.md (ако съществува)
3. ПОТВЪРЖДАВА:
   "⚡ Context Refresh:
   - Работим по: [задача]
   - Режим: [NORMAL/REPAIR/...]
   - Следваща задача: [от TODO.md]
   - Проблеми: [от PROBLEMS.md]
   - Последни решения: [от DECISIONS.md]
   Правилно ли е?"
4. ПРОДЪЛЖАВА след потвърждение
```

### 5. ЗАДЪЛЖИТЕЛЕН BACKUP

Преди редакция на работещ код → копирай в .memory/backups/

```
ПРЕДИ да редактираш работещ код:
1. КОПИРАЙ оригинала в .memory/backups/
2. Формат: YYYY-MM-DD_HH-MM_filename.bak
3. ЧЕТИ ЦЕЛИЯ файл (правило 3)
4. Едва тогава редактирай

НЕ разчитай на:
- "Ще го възстановя от паметта"
- "Имам го в Git"
- "Само малка промяна е"
```

**Пример:**
```
❌ ГРЕШНО: "Ще променя само този ред" → чупи целия скрипт
✅ ПРАВИЛНО: "Първо backup... Готово. Сега да прочета целия файл... Сега редактирам"
```

---

### 6. ЗАЩИТЕНИ ЗОНИ

Не пипай критични папки без Backup + User Approval

```
Някои папки/файлове са СВЕЩЕНИ:
- Дефинирани в .memory/PROTECTED.md (ако съществува)
- Production код
- Конфигурационни файлове
- База данни файлове

За тях ВИНАГИ:
1. Backup ПЪРВО
2. User Approval ПРЕДИ промяна
3. Никакво директно триене/местене
```

**Пример:**
```
❌ ГРЕШНО: "Ще изтрия тези стари файлове от production/"
✅ ПРАВИЛНО: "Тази папка изглежда важна. Да питам преди да пипам нещо"
```

---

### 7. ВЕРИФИЦИРАЙ

Не приемай резултат "на сляпо", провери с втори източник

```
Не приемай резултат само защото "изглежда правилен":
- Провери с втори източник когато е възможно
- При работа с база данни → провери и файловата система
- При критични операции → double-check

НИКОГА не казвай "Готово!" без да си сигурен.
```

### 10. ГОЛЕМИ ЗАДАЧИ = МАЛКИ СТЪПКИ

Ако файл >150 реда или >2 файла → раздели на стъпки, покажи план, чакай одобрение

```
КОГА СЕ АКТИВИРА:
- Файл > 150 реда
- Задача засяга > 2 файла
- Има връзка с база данни / API / файлова система
- Потребителят каже "сложно" или "голямо"
- Агентът се съмнява в обхвата

КАКВО ПРАВИМ:
1. СТОП — не започвай веднага
2. АНАЛИЗ — прочети всичко свързано
3. ПЛАН — раздели на стъпки (макс 1 промяна на стъпка)
4. ПОКАЖИ ПЛАНА — изчакай одобрение
5. ИЗПЪЛНИ СТЪПКА 1 → тествай → потвърди
6. ИЗПЪЛНИ СТЪПКА 2 → тествай → потвърди
7. ... и така докато готово
```

**Пример:**
```
❌ ГРЕШНО:
"Ще оправя скрипта"
→ 8 поправки после защото нещо е пропуснато

✅ ПРАВИЛНО:
"Виждам че задачата е сложна. Ето моя план:
1. [ ] Прочета целия скрипт (~300 реда)
2. [ ] Backup на оригинала
3. [ ] Разбера връзките с базата данни
4. [ ] Оправя database заявката
5. [ ] Тест на стъпка 4
6. [ ] Оправя HTML генерирането
7. [ ] Тест на стъпка 6
8. [ ] Финален тест с реални данни
Одобряваш ли този план?"
```

## ПАМЕТ ДИСЦИПЛИНА (Ново в v2.0)

### 12. ПАМЕТ СИНХРОН

След работа обнови ВСИЧКИТЕ засегнати: STATE + LOG задължително; TODO / DECISIONS / PROBLEMS / ARCHITECTURE при промяна. Една секция update без останалите = drift.

### 13. TODO = ОТПРАВНА ТОЧКА

TODO.md е входът и изходът на сесията. Начало: чети TODO. Край: актуализирай TODO. Ако задача не е в TODO → питай дали е легитимна.

### 14. INBOX ВИНАГИ ЧИСТ

`.requests/inbox/` не съдържа необработени файлове. В начало на сесия: провери inbox → обработи всеки в CR (по TEMPLATE.md) → премести оригиналите в archive/originals/ → обнови REGISTRY.md + LOG.md. Inbox = вход, не склад.

### 15. СТРОГО СТРУКТУРА НА ПАМЕТТА

В .memory/ root живеят САМО 8-те стандартни файла (STATE, LOG, TODO, DECISIONS, PROBLEMS, MODE, TOOLS, ARCHITECTURE). Всичко друго в subdirectory: планове → plans/, анализи → analysis/, research → architecture/research/, фази → phase_a/ phase_b/, скриптове → scripts/, backups → backups/. Ad-hoc в root = забранено.

## РЕЛИЙС И ПУБЛИКАЦИЯ (Ново в v2.0)

### 16. AUDIT ПРЕДИ PUBLISH

Преди git push към публичен repo или npm publish: задължителен code audit (URLs, README, changelog, критични files). Не публикувай "работещо локално" без audit.

### 17. SMOKE TEST ПРЕДИ COMMIT

Build + мин 3 basic CLI проверки (version, help, no-op) преди git commit. Ако tsc не минава → не commit-вай.

### 18. ПАМЕТТА = РЕАЛНОСТ, НЕ НАМЕРЕНИЕ

LOG.md описва какво СЕ Е СЛУЧИЛО, не планирано. ⏸️ отложено / ❌ неуспешно / ⏳ предстои / ✅ завършено.

### 19. НЕ БЪРЗАЙ

Малки проблеми сега (typo, wrong URL, липсващ bullet) = emergency patches после. Ако не си сигурен → спри, провери.

## ПРАВИЛА И АРХИТЕКТУРА (Ново в v2.0)

### 20. ПРАВИЛАТА ПЪРВО

Преди STATE/TODO/каквото и да е — прочети CLAUDE.md (IRON RULES). Правилата са контекст за всяка друга стъпка. Това е ПЪРВАТА стъпка на session start.

### 21. ЕДИН ИЗВОР НА ПРАВИЛАТА

Пълните правила живеят в project CLAUDE.md. User global (~/.claude/CLAUDE.md) е само pointer + лични preferences. Другите IDE файлове (.cursorrules, .antigravity/rules.md) са IDENTICAL mirrors, поддържани от `svetlio upgrade`. Не редактирай ръчно IDE-specific файлове — промените се правят в template-а и се регенерират.

### 22. ПРОДУКТОВ REPO ≠ DEV MEMORY

Продуктовите repos (Office, Docs, 30doc, Education, Personal, ai-svetlio tool) НИКОГА не комитват `.memory/` в public git. Dev memory живее в **private Hub** (през `svetlio sync`). Публичен repo = код + docs + README. Точка.

**Why:** Business decisions, client names, revenue numbers, incident history, strategy — никое не принадлежи в public git. Веднъж leaked = forever indexed.

**How to apply:** `.memory/` в `.gitignore` от ден 1 на всеки нов публичен repo. Hub Sync = единствен път за споделяне. Pre-push audit: ако `.memory/` е tracked в public repo → BLOCK.

## 📊 Бърз справочник: Прагове

| Критерий | Праг | Действие |
|----------|------|----------|
| Редове код | > 150 | Big Task Protocol |
| Брой файлове | > 2 | Big Task Protocol |
| Има DB/API | винаги | Big Task Protocol + Backup |
| Съобщения в чата | ~15 | Context Refresh |

## ⚠️ Споделена отговорност

Паметта на Светльо е **споделена отговорност** между потребителя и AI агента. AI агентът записва в `.memory/` само ако потребителят му даде време да завърши. Ако сесията бъде затворена преди записа — паметта остава неактуална.

**При приключване на сесия:**
1. Обнови `.memory/STATE.md` и `LOG.md` (ВИНАГИ)
2. Обнови `TODO.md`, `PROBLEMS.md`, `DECISIONS.md` (ако има промени)
3. Потвърди на потребителя, че записът е завършен
4. Едва тогава потребителят затваря чата

> 📖 Пълна документация: [USER_GUIDE.md](./USER_GUIDE.md#-споделена-отговорност--как-работи-паметта)
